# 1.3 增量计划：网页与 RTMP 分享、H.264 / HEVC 及硬件加速

状态：1.3.0 实现与验收通过。基线 1.2.0；主 agent 统一集成、桌面检查与 release/ 交付。用户要求保留 URL、提供 RTMP 源、取消导出 URL 文件，并支持 H.264 / HEVC 与硬件加速。

## 产品行为与范围

- 继续提供网页邀请、观看码、二维码和接收页地址导入；彻底移除 `.url` 文件导出入口、IPC、辅助模块与对应测试。
- 默认同时启用 RTMP，可关闭以减少资源占用。GUI 配置 RTMP 本机 TCP 端口（默认 1935）及一级网络映射端口（默认 1935），自动保存；网页及 RTMP 不得占用同一 TCP 端口。
- 分享区域并列显示网页邀请和 RTMP 地址，分别复制；LAN / 一级网络切换同时更新两者。RTMP 使用随机会话路径，不持久化，停止后失效。准备、可用、失败状态明确，失败不停止网页。
- RTMP 提供 H.264 / HEVC 和硬件优先 / 仅硬件 / 软件编码；默认 H.264 + 硬件优先。H.264 / AAC 兼容常见播放器，HEVC / AAC 使用 Enhanced RTMP，接收软件也需支持。现有网页 HEVC / H.264 / VP8 设置保留。复用最终混合 MediaStream，保持相同屏幕 / 窗口、系统声音、麦克风、实时音量与静音，不二次抓屏。
- 两种协议合计受同一个 maxViewers 限制，沿用 bitrateMbps × maxViewers <= 70 Mbps；RTMP 增加 TCP 映射提示。RTMP 本身的播放延迟取决于播放器缓存，不能将本机可解码报告为实测端到端低延迟。
- 原生依赖随包离线提供，固定版本与 SHA256，控制 API / 认证仅监听 loopback；不增加公网云服务，不自动写路由器端口映射。

## 已验证的方案与验收边界

2026-10-13 当前 Electron 44.7.0 实际 MediaRecorder 探测：Matroska avc1/opus 输出被 ffprobe 识别为 H.264 + Opus；MP4 avc1/AAC 也可录制，但分片间隔更大，记录为 `.cache/rtmp-codec-probe.json`。随后用户追加 H.264 / HEVC 与硬件加速要求：录制优先短分片 VP8/Opus，浏览器拒绝时允许受限 Matroska H.264/Opus 备选，二者均交 FFmpeg 编码为目标格式。真实短帧编码决定硬件可用性，auto 无硬件时保留同一目标编码的软件回退。不能把 copy 宣称为硬件加速证据。

MediaMTX 1.21.2 提供 RTMP 接收 / 分发、HTTP 认证和 Control API。开发用 BtbN 构建发现第三方许可冲突，交付改用固定 FFmpeg 源码自编译的最小 LGPL shared 构建，带 Windows MF、NVENC 与 BSD Kvazaar；最终版本为 FFmpeg 8.1.3-lan-cast-1，构建参数、全部原生文件 SHA256、许可及对应源码归 vendor/media/manifest.json 与随包文件核定。源码桌面验收已确认默认 15 秒媒体启动期限内可用，H.264 / HEVC 的 NVENC 硬件、MF H.264 软件及 Kvazaar HEVC 软件均真实解码成功。未编译或设备不支持的硬件候选会实际失败并尝试后续候选，不能宣称全显卡支持。具体播放器、其他 GPU 及端到端延迟仍需现场验证；不能凭 MIME 声明或子进程启动宣布可用。

AudienceRegistry(maxViewers) 为同步容量边界：admit(id,{name,address,protocol}) -> bool（同 id / 协议幂等），remove(id)、has(id)、get(id)、size、viewers；事件 joined(viewer)、left(viewer)、changed(viewers)。RTMP id 为 `rtmp:<MediaMTX connection UUID>`，网页 id 保持 UUID。认证成功先占位；Control API 确认结束后释放，未建立的占位只有证实连接不存在才能限时回收。无法监测时关闭 RTMP，证实服务退出后释放容量；退出失败保留 owner 和占位，阻止新的广播，下一次停止或开始重试清理。

RtmpSession(config,{audience,binDir,tempRoot}) extends EventEmitter：prepare()、begin({mimeType}) -> {generation}、append({generation,sequence,bytes}) -> ACK、finish({generation,message?})、stop()、kick(id)、updateAdvertisedHost(address)、getInfo()。state 事件 payload 与 getInfo() 相同：{enabled,phase,message,localUrl,forwardedUrl,codec,encoder,hardware,uploadMbps}，phase 为 preparing / waiting / starting / ready / error / stopped。配置已严格验证。只允许已知 Matroska avc1/opus 或 WebM vp8/opus MIME；通过 selectRtmpEncoder 取得目标视频 args，音频固定 AAC。ready 需确认 MediaMTX 路径有媒体。服务错误只影响该旁路；stop 幂等、准备期间可取消。

追加配置：rtmpCodec='H264'|'HEVC' 默认 H264，rtmpAcceleration='auto'|'hardware'|'software' 默认 auto，GUI IDs rtmp-codec / rtmp-acceleration，由 share.getConfig()/loadSettings 管理。selectRtmpEncoder(config,{ffmpegPath,signal,...testDependencies}) -> {codec,encoder,hardware,label,args}，args 为可直接插入长驻 FFmpeg 的固定 video argv；硬件探测使用实际短帧编码，不依赖 encoders 列表。硬件模式无可用编码器明确失败，仅 RTMP 失效；auto 在全部硬件失败后使用同 codec 软件路径并显示回退；software 禁用硬件选择。每次启动检查取消，探测超时有界，只终止自己拥有的进程。未证实的软件 HEVC 不宣称支持。

IPC 仅暴露 beginRtmp({roomId,mimeType})、appendRtmp({generation,sequence,bytes})、finishRtmp({generation,message?})，既有可信主 frame 校验保留。主进程只根据自己的路径和配置生成命令；不接收可执行路径、任意参数或任意发布地址。rtmp-state 事件为 {roomId, ...getInfo()}，跨会话丢弃。

createRtmpRecorder({stream,config,roomId,api,onError}) -> {start(),dispose()}。api 的 beginRtmp / appendRtmp / finishRtmp 对应 preload，start() 使用支持的 VP8/Opus，拥有 recorder，在 async 返回后再次核对取消；默认 timeslice 100 ms、关键帧 1 秒。一片最大 4 MiB、全部在途 / 排队最多 8 MiB、最老片等待最多 3 秒；仅一个 IPC 写入在途，禁止丢片后继续同一容器。失败停止 RTMP、清空队列并说明原因，网页继续。dispose 不停止共享媒体轨道，不能等未完成 Blob 转换才能生效。

GUI IDs：rtmp-enabled、rtmp-port、advertised-rtmp-port（config-control），rtmp-link、copy-rtmp、rtmp-status。share.getConfig() 返回以上新字段；share.updateRtmp(payload) 用 roomId 丢弃旧状态。sessionInfo.rtmp 为 getInfo()；rtmp ready 才允许复制播放地址。host.js 主 agent 调用 recorder，并为 RTMP 观看者跳过 WebRTC add / signal，显示协议及编码。

## 验收与顺序

集成审查补充合同：

- 录制优先 VP8/Opus，浏览器拒绝时允许受限 Matroska H.264/Opus 备选；二者均重新编码到所选目标，不能用 copy 宣称硬件加速。
- selectRtmpEncoder 的 onProcess(child) 将探测进程交给 RtmpSession 管理；未证实退出时停止选择，不启动下一个候选，不遗失 child。
- RTMP error / stopped 立即 dispose 同 room 的 recorder，保留共享轨道和网页广播。
- 停止 native 失败时明确拒绝，BroadcastSession.retired 保留旧 owner，busy 阻止新广播；下一次停止 / 选择来源先重试回收，退出证实后释放旧容量。关闭失败允许再次关窗重试，不永久缓存失败。
- 无声音时不显示 AAC；启用声音时 ready 检查 AAC。HEVC 接收 FFmpeg 在 -i 前增加 -rtmp_enhanced_codecs hvc1，保留传统 H.264 接收检查。

1. 并行实现后 root 读取实际修改，检查 IPC、取消、资源归属、认证、两协议容量、配置兼容和旧导出调用者。
2. Node：旧回归 + 共享容量 / 配置 / RTMP 生命周期、严格消息 / 有界背压、认证与监听目标、旧 generation、录制队列 / Blob 迟到和失败隔离、分享目标 / RTMP 状态。
3. root 串行真实 Electron：原有 smoke / GUI / features / system-audio；新增 rtmp-smoke 实际采集与最终混合音轨，经随包 FFmpeg + MediaMTX 生成 H.264 硬件 / 软件、HEVC 硬件 / 软件四组 RTMP，再真实解码视频帧和 AAC / PCM 音频。同时打开生产网页接收端、核对合计人数上限、停止端口及进程释放、旧地址失效、导出 API / 控件消失、服务失败时网页继续。
4. 未编写相应模块的 agent 独立审查；修复有影响的问题后重验。
5. 1.3.0 构建便携 EXE 与解压 ZIP，原生依赖在 resources/media 的 ASAR 外。生产指纹、bundle 检查和 runtime evidence 包含 manifest 与实际原生文件 SHA256；源 / 打包的 RTMP 报告均为交付门禁。
6. 打包目录重复媒体 / GUI 验证，便携单文件启动，ZIP CRC 与内含文件哈希；更新根计划、结构、网络指南、验证与项目 skill。保留旧版本 EXE / ZIP，不触碰真实用户配置。远程 / 外部安装目录保持未配置状态。

现场边界：物理 1–5 台、校园网真实跨 NAT、100 Mbps 限速、游戏、高负载与端到端延迟未有新证据时仍标为未测；本机 RTMP 解码不冒充 PotPlayer GUI 现场测试。
